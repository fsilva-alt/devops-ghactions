Ambiente de prática

Automatizar é transformar uma sequência de passos em um processo que você pode repetir e conferir.

O projeto já está pronto

Um cardápio em Python, três testes e um gerador de HTML. Você vai aprender a descrever o processo em YAML. Precisa conhecer commit, branch e push; os comandos de publicação estão nos enunciados.

Codespace: seu editor e terminal no navegador, obrigatório nos 7 exercícios.

WORKFLOW · JOB · STEP

Primeiro workflow

Crie um workflow com execução manual e confira a mensagem nos logs.

As partes da automação

Workflow: arquivo YAML que descreve o processo.

Evento: o que inicia a execução; aqui, workflow_dispatch, um clique manual.

Job: grupo de etapas que executa em um runner.

Runner: máquina que executa o job.

Step: cada etapa da lista steps.

YAML usa espaços para a indentação. O traço inicia um item da lista. Salve o arquivo em .github/workflows/ci.yml.
name: Boas-vindas

on:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  boas-vindas:
    runs-on: ubuntu-latest
    steps:
      - name: Cumprimentar a turma
        run: echo "Olá, GitHub Actions!"

Pratique no Codespaces

cd ~/labs/01-primeiro-workflow
code .github/workflows/ci.yml
check.sh 01
  1. Crie e salve o arquivo com o exemplo acima.
  2. Confira com o check, faça commit e publique em actions-01.
  3. Abra Actions → Boas-vindas → Run workflow. Selecione main.
  4. Abra o job e a etapa para localizar a saudação no log.

Sua entrega

Link da execução manual verde e a mensagem Olá, GitHub Actions! no log.

O echo executou no Codespace ou em um runner?

Em um runner do Actions. O Codespace foi usado para escrever e publicar o workflow.

Se não houver execução após o push, está correto: neste exercício o único evento é manual. O botão aparece quando o workflow está na branch padrão.

PUSH · USES · RUN

Testes no push

Configure o ambiente do runner para executar os testes a cada push.

Integração contínua

CI significa integração contínua: verificar mudanças automaticamente.

uses chama uma action pronta, com versão explícita.

with configura as entradas dessa action.

run executa um comando no runner.

Checkout vem primeiro porque o runner precisa receber os arquivos do projeto. As etapas de um job executam em sequência.
name: CI

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  testar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: '3.12'
      - run: python -m pip install -r requirements.txt
      - run: python -m unittest -v

Pratique no Codespaces

cd ~/labs/02-testes-no-push
python3 -m unittest -v
code .github/workflows/ci.yml
check.sh 02
  1. Execute os três testes prontos e procure OK.
  2. Substitua a saudação pelo workflow acima.
  3. Confira, faça commit e publique em actions-02.
  4. Edite o título do cardápio, faça novo commit e push. Acompanhe outra execução.

Sua entrega

Uma execução verde disparada por push, com três testes aprovados. Localize o hash do commit na página da execução.

Instalar no Codespace também instala no runner?

Não. São máquinas separadas. O workflow precisa preparar seu próprio ambiente: código, Python e dependências.

Use '3.12' entre aspas: é uma versão, não um número decimal.

PULL_REQUEST · LOGS · CORREÇÃO

Checks no pull request

Analise os logs de um teste com falha e corrija o código antes de integrar a mudança.

Verificação de pull requests

pull_request executa os testes quando um PR é aberto ou atualizado. O filtro branches indica o destino do PR.

Abra a etapa que falhou. Compare o valor esperado com o recebido. O teste de três unidades espera 1500 centavos, mas a soma incorreta retorna 503.

Cada execução corresponde a uma revisão do código. Reexecutar um commit quebrado não aplica a correção que ainda está só no Codespace.
# Substitua apenas o bloco on:
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:
# Falha proposital em app.py:
return preco_centavos + quantidade

# Correção:
return preco_centavos * quantidade

Pratique no Codespaces

cd ~/labs/03-checks-no-pull-request
code .github/workflows/ci.yml
check.sh 03
  1. Acrescente o evento e publique a main em actions-03.
  2. Crie a branch teste-do-ci. Troque a multiplicação por soma em app.py.
  3. Faça commit, push e abra o PR para main. Leia o erro em Checks → testar → Testar.
  4. Corrija a multiplicação. Faça novo commit e push na mesma branch e confira o novo check.

Sua entrega

Link do PR e das execuções vermelha e verde. Explique qual linha causava o erro. O PR pode ficar aberto para avaliação.

Um check vermelho sempre impede o merge?

Só quando regras do repositório exigem aquele check. Aqui aprendemos a observar e interpretar o resultado.

ENV · INPUTS · VARS · SECRETS

Variáveis e contextos

Configure uma execução manual com variáveis e contextos e identifique a origem dos valores usados.

Origem dos valores

env define variáveis no YAML, como o nome do curso.

inputs recebe a mensagem digitada em Run workflow.

github traz informações da execução, como quem a iniciou.

vars lê variáveis das configurações do repositório.

secrets lê valores cadastrados como segredos.

O Actions avalia ${{ }}; o shell lê $VARIAVEL. O exemplo passa a mensagem por env para tratá-la como texto, inclusive quando contém aspas.

Trechos de duas etapas. Use o exemplo completo indicado na prática.

# Na etapa Mostrar contexto:
env:
  MENSAGEM: ${{ inputs.mensagem }}
  AUTOR: ${{ github.actor }}
  TURMA: ${{ vars.TURMA }}
run: |
  printf '%s\n' "$MENSAGEM"
  printf '%s\n' "$AUTOR" "$TURMA"

# Em outra etapa, sem imprimir o segredo:
env:
  TOKEN_DEMO: ${{ secrets.CURSO_TOKEN }}
run: test -n "$TOKEN_DEMO"

Um segredo de demonstração

Cadastre CURSO_TOKEN com o valor fictício somente-demonstracao. O comando test -n verifica se o valor não está vazio, sem exibi-lo no log.

Pratique no Codespaces

cd ~/labs/04-variaveis-e-contextos
cp "$CURSO_DIR/docs/solucoes/04.yml" .github/workflows/ci.yml
code .github/workflows/ci.yml
# Personalize e salve antes de conferir:
check.sh 04
  1. Mude o default da entrada mensagem e localize env.CURSO.
  2. Confira, faça commit e publique em actions-04.
  3. Em Settings → Secrets and variables → Actions, crie a variável TURMA e o segredo fictício CURSO_TOKEN, nas respectivas abas.
  4. Execute manualmente na main com uma mensagem sua. Leia os logs e a confirmação de presença do segredo.

Sua entrega

Uma execução manual verde com mensagem personalizada, autor, turma e segredo verificado sem exibir seu valor.

Qual a diferença entre vars e secrets?

Ambos vêm das configurações do repositório. Use vars para configurações comuns e secrets para valores sensíveis. No curso, o segredo é fictício e só verificamos sua presença.

O check local confere as referências no YAML. Se a última etapa falhar no Actions, confira o nome do segredo e o repositório em que foi cadastrado: um segredo ausente resulta em valor vazio.

NEEDS · RUNNER · BUILD

Jobs e dependências

Defina a dependência entre os jobs de testes e build e verifique o comportamento quando um teste falha.

testar→empacotar

Dependências entre jobs

Etapas de um job executam em sequência. Jobs sem dependências podem executar em paralelo.

needs: testar faz empacotar aguardar os testes e prosseguir somente se eles passarem.

Build: neste projeto, python build.py transforma cardapio.md em dist/index.html.

Cada job recebe seu próprio runner. Por isso, o build também precisa de checkout, Python e instalação das dependências.

Acrescente dentro de jobs, no mesmo nível de testar, com dois espaços de indentação.

empacotar:
  needs: testar
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v5
    - uses: actions/setup-python@v6
      with:
        python-version: '3.12'
    - run: python -m pip install -r requirements.txt
    - run: python build.py
    - name: Conferir o arquivo gerado
      run: test -s dist/index.html

Conferir o build

test -s retorna sucesso quando o arquivo existe e não está vazio. O resultado ainda está somente no runner.

Pratique no Codespaces

cd ~/labs/05-jobs-e-dependencias
code .github/workflows/ci.yml
check.sh 05
  1. Preserve testar e acrescente o job empacotar.
  2. Confira, faça commit e publique em actions-05. Veja o grafo da execução.
  3. Em app.py, troque temporariamente a multiplicação por soma. Faça commit e push na main. Observe o build como skipped (pulado).
  4. Corrija a multiplicação, faça outro commit e push. Termine com os dois jobs verdes.

Sua entrega

Execução final verde e uma execução anterior com o build pulado após a falha dos testes.

Os arquivos de testar aparecem em empacotar?

Não. Jobs separados não compartilham automaticamente o sistema de arquivos. As etapas do mesmo job compartilham seus arquivos. needs define a dependência, mas não copia arquivos.

UPLOAD-ARTIFACT · DOWNLOAD

Artefatos do build

Armazene os arquivos gerados como artefatos para baixá-los após a execução.

Armazenamento de artefatos

Um artefato guarda arquivos de uma execução para consulta ou distribuição. Pode ser um site, relatório ou pacote.

Aqui, name: site identifica o artefato e path: dist/ escolhe os arquivos enviados.

retention-days: 7 solicita que o resultado fique disponível por sete dias.

O upload vem depois do build. Guardar o ZIP como artefato ainda não publica o site na web.

Última etapa de jobs.empacotar.steps. Alinhe o traço com o das outras etapas.

- name: Guardar o site
  uses: actions/upload-artifact@v4
  with:
    name: site
    path: dist/
    if-no-files-found: error
    retention-days: 7

Quando nenhum arquivo é encontrado

if-no-files-found: error faz a etapa falhar se não houver arquivos para enviar. Confira se o build terminou e se a pasta é dist/.

Pratique no Codespaces

cd ~/labs/06-artefatos-do-build
code .github/workflows/ci.yml
check.sh 06
  1. Adicione o upload no final das etapas de empacotar.
  2. Confira, faça commit e publique em actions-06.
  3. Depois da execução, encontre Artifacts → site no resumo. Logado no GitHub, baixe o ZIP e abra index.html.
  4. No Codespace, personalize o título do cardápio, faça commit e push. Baixe o artefato da nova execução e compare o título.

Sua entrega

Link da execução final e confirmação de que o artefato site contém index.html com seu título atualizado.

Onde procurar o artefato de uma versão anterior?

Na execução daquele commit, enquanto o artefato não tiver expirado ou sido removido. Cada execução tem seu próprio resultado.

TESTAR → GERAR → PUBLICAR

Deploy no Pages

Publique o site no GitHub Pages com o workflow fornecido, que reúne testes, build e deploy.

testar→empacotar→publicar

Etapas de publicação

testar verifica o código. Se passar, empacotar gera o HTML, prepara o Pages com actions/configure-pages e envia o site com actions/upload-pages-artifact.

publicar usa actions/deploy-pages para disponibilizar esse artefato no endereço do site.

O job de publicação recebe pages: write e id-token: write. O GitHub fornece a credencial da execução; não é necessário cadastrar um token pessoal.

Job final do exemplo. O arquivo completo também contém os testes e o build.

publicar:
  needs: empacotar
  if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
  runs-on: ubuntu-latest
  permissions:
    pages: write
    id-token: write
  environment:
    name: github-pages
    url: ${{ steps.deploy.outputs.page_url }}
  steps:
    - name: Publicar
      id: deploy
      uses: actions/deploy-pages@v4

Publicar somente a main

A condição if permite a publicação da main por push ou execução manual e exclui PRs. Os PRs continuam executando testar.

O environment github-pages identifica o destino e exibe a URL devolvida pela etapa deploy.

Pratique no Codespaces

  2. Volte ao Codespace e copie o workflow guiado com os comandos abaixo. Leia o fluxo com o professor.
  3. Personalize o título de cardapio.md. Rode o check, faça commit e push.

Qual é a diferença entre build, artefato e deploy?

Build gera os arquivos. Artefato guarda os arquivos. Deploy disponibiliza o resultado em seu destino, aqui o Pages.

E se o site ainda não abrir?

Aguarde alguns minutos após a publicação. Se o workflow falhou, confirme a configuração em Settings → Pages e compare permissions e environment com o exemplo. Após corrigir, use Actions → Publicar no Pages → Run workflow → main.
